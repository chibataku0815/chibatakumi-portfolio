## 4. Investigation plan (as designed in plan mode)

Four parallel Explore-agent streams were launched in a single message
to map to the four hypotheses. Each stream had a focused prompt with
repo path, branch, HEAD, constraints, and a specific evidence
requirement. All four ran read-only.

| Stream | Target hypothesis | Scope |
|---|---|---|
| **A** | H1 / H2 | Historical flag audit + `.env*` / build-define audit |
| **B** | H3 | App-shell compare driver wiring on WebGPU |
| **C** | H4 | Static validation of the new pipelines in `8774de55` |
| **D** | H4 + state path | Complete runtime state map: `envPref → init → caps → gate` |

Rationale for four streams (not fewer):

- H1 vs H2 are symmetric but mutually exclusive and cheap to resolve
  in parallel. Folding them would serialize trivially parallel git
  reads.
- H4 needed a **code-side** check (Stream C) *and* a **state-flow**
  check (Stream D) because a pipeline validation error manifests
  differently depending on where the init path catches it. Splitting
  gave two independent lenses on the same hypothesis.
- Three streams would have collapsed C and D — and Stream C ended up
  making a high-confidence error that Stream D's independent analysis
  partially inoculated against. Worth the extra stream.

**Verdicts**:

- **H1 CONFIRMED.** WebGPU's `supportsBeforeAfter` and
  `supportsABCompare` have been `false` since the WebGPU capability
  surface was introduced in commit `3e205386` (2026-04-18 23:20:19

- **H2 REJECTED.** No `.env*` file in repo contains `FILMTONE_BACKEND`.
  `vite.config.ts:126` hard-codes

  +0900). There is no WebGL override for this user to have lost.
- Diff confirmed `8774de55` did not touch `GpuContext.ts`,
  `Viewport.ts`, or `FilmLabCanvas.tsx`.

### 5.2 Stream B — H3

- Grep-audited `setComparePair`, `abCompareEnabled`, `compareHud`,
  `comparePair`, `splitPosition`, `supportsABCompare`,
  `supportsBeforeAfter` across the full repo.
- Read the compare-bar gate region of `FilmLabCanvas.tsx`
  (lines 1150–1710).
- Read `Viewport.ts:330-336` — the delegate method.
- Surveyed `WebGPUBackend.ts` for any compare method or stub.

**Verdicts**:

- **H3 mechanism refined.** `Viewport.ts:330-336` defines
  `setComparePair` as an optional-chain delegate to `webglBackend`.
  On WebGPU `webglBackend` is `null`, so any direct call to that
  method is a silent no-op. However, the UI never reaches this point
  on WebGPU because **the gate at `FilmLabCanvas.tsx:1159` short-
  circuits earlier**: `previewSupportsCompare === false` removes the
  HUD render, the cursor class, and the pointer/drag handlers before
  any compare driver wiring is even attached.
- `WebGPUBackend.ts` has `frameState.splitPosition: -1` as a stored
  field only. There is no `setComparePair` method, no compare render
  path, no WGSL split / A-B blend shader. This matches part-6 §6.6 —
  Split / A-B compare is listed there as an explicit defer.
- `compareHud` is computed regardless of backend, then UI-gated at
  line 1617. The gate filter is the only place WebGPU divergence is
  enforced.

### 5.3 Stream C — H4 (static validation of new pipelines)

- Read the three new WGSL shader modules
  (`cross-filter-temporal.frag.wgsl.ts`,
  `lightshafts-radial.frag.wgsl.ts`,
  `lightshafts-blend.frag.wgsl.ts`) and the three new JS bind-group
  layouts (`crossFilterTemporalGroupLayout`, `lightshaftsGroupLayout`,
  `lightshaftsBlendGroupLayout`).
- Checked uniform buffer byte sizes vs WGSL struct sizes.
- Checked fragment target formats (`rgba16float`).
- Checked the orientation-contract rebinding required by part-7 §3.2.
- Checked device feature requests in `GpuContext.ts`.

**Stream C's reported verdict**:

- **Claimed H4 live**: `lightshaftsBlendGroupLayout` allegedly
  declared only 3 bindings (0, 1, 2) while the WGSL required 4
  (0, 1, 2, 3 including the sampler) — Stream C argued this would
  fail pipeline validation, preventing backend init and leaving
  `viewportCapabilities = null`.
- All other layouts reported as matching their WGSL.
- Uniform sizes reported as correct (16-byte aligned).
- Orientation contract reported as correctly rebound to
  `crossFilterFlagsBindGroup`.

**This chat's verification of Stream C's critical claim**:

A direct re-read of
`packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts:582-590` was
performed in the main context. The layout definition is:

```ts
const lightshaftsBlendGroupLayout = device.createBindGroupLayout({
  label: "lightshafts.blend.group1",
  entries: [
    { binding: 0, visibility: GPUShaderStage.FRAGMENT, buffer: { type: "uniform" } },
    { binding: 1, visibility: GPUShaderStage.FRAGMENT, texture: { sampleType: "float" } },
    { binding: 2, visibility: GPUShaderStage.FRAGMENT, texture: { sampleType: "float" } },
    { binding: 3, visibility: GPUShaderStage.FRAGMENT, sampler: { type: "filtering" } },
  ],
});
```

All 4 bindings are present and match the WGSL `@binding(0..3)`.
**Stream C's report was a miscount.** The pipeline layout is valid.
H4's "static smoking gun" does not exist.

This is recorded explicitly because a future investigator reading
part-8 and part-9 should not reopen H4 based on Stream C's report
alone — the evidence has been independently verified.

## 6. Synthesis & final diagnosis

The four streams converge on:

- **H1**: ✅ confirmed (Stream A evidence; consistent with Stream B,
  Stream D).
- **H2**: ❌ rejected (Stream A evidence).
- **H3**: ❌ rejected as the *cause*; true as a *mechanism note* — the
  driver would be a no-op on WebGPU even if the UI tried, but the UI
  short-circuits first (Stream B evidence).
- **H4**: ❌ no static evidence, after Stream C's claim was verified
  and found to be a miscount (Stream C + direct re-read + Stream D
  runtime-path reasoning). Not bulletproof — a runtime validation
  error could still exist in some pipeline path Stream C did not
  inspect — but the user's report ("compare bar missing", not "app
  broken") is consistent with the WebGPU success path, so H4 is
  extremely unlikely.

**Single-sentence diagnosis**: the compare bar is gated off on
WebGPU by design for v1; the user's Desktop build defaults to WebGPU
per the Vite build flag; therefore the compare bar does not appear.
Not a regression.
