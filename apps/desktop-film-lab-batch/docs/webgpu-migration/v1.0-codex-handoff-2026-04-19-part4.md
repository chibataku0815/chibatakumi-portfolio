## 3. What landed in the latest implementation session

The part 3 handoff listed four concrete issues as the immediate next
work. Those are now implemented in `da74f188`.

### 3.1 Export hotfix bundle is now landed

The following issues from part 3 are fixed:

#### 3.1.1 WebCodecs + WebGPU export freeze after the first frame

Root cause in part 3:

- `webgpu-offscreen-render-session.ts` snapshots non-video
  `CanvasImageSource` inputs via `createImageBitmap(...)`
- the WebCodecs export path used a `CanvasTexture`
- `video-export-pipeline.ts` only flipped `srcTexture.needsUpdate`
  after frame advance, but the WebGPU offscreen session needed a fresh
  upload, not just a needsUpdate flag

What landed:

- On the `WebCodecs + WebGPU` path, for frames that actually advance
  (`!reuseFrame`), the export loop now re-runs
  `await renderSession.setSource(...)` before `renderSession.render()`
- HTMLVideoElement and reused-frame behavior remain unchanged

Effect:

- WebGPU export no longer freezes after the first decoded frame simply
  because the offscreen upload stayed stale

#### 3.1.2 Frame 0 ffmpeg drop is now backend-aware

Root cause in part 3:

- `apps/desktop-film-lab-batch/electron/main.ts` used an unconditional
  rawvideo filter chain containing
  `select=gte(n\,1),setpts=N/FRAME_RATE/TB`
- that was historically a workaround for a WebGL first-frame issue
- on the new WebGPU readback path it was wrong, because it dropped the
  real first frame and could shorten audio due to `-shortest`

What landed:

- `videoExportStart` now accepts `dropFirstFrame: boolean`
- the renderer sends `dropFirstFrame: renderSession.backendKind === "webgl"`
- ffmpeg keeps the old frame-0 drop only for WebGL exports
- WebGPU exports now use the same color conversion path without the
  `select=gte(n\,1)` stage

Effect:

- WebGPU export preserves the real first frame
- audio is no longer shortened for that reason on the WebGPU path

#### 3.1.3 Stale WebGL2-only preflight is now removed from the WebGPU-first paths

Root cause in part 3:

- both the batch and video export pipelines still hard-failed on
  `!isWebGL2Supported()`
- but those same pipelines already requested `prefer: "webgpu"` for the
  offscreen session and no longer used backend fallback

What landed:

- batch and video export now gate on `isWebGPUSupported()`
- user-facing messages were updated accordingly

Effect:

- preflight now matches the actual backend policy instead of rejecting a
  valid WebGPU-capable environment because of an irrelevant WebGL2 check

### 3.2 Preview parity bundle is now landed

The following part 3 preview gaps are fixed:

#### 3.2.1 `aberrationEdgeSoften` is now derived correctly in WebGPU

Root cause in part 3:

- WebGL derives `uAberrationEdgeSoften = clamp(rgbShift * 32, 0, 1)`
- WebGPU read a direct `aberrationEdgeSoften` param that the shared
  params model never supplies
- so WebGPU effectively saw `0` unless an out-of-band key was injected

What landed:

- `packages/film-lab-renderer/src/webgpu/compositeUniforms.ts` now
  derives `aberrationEdgeSoften` from `rgbShift * 32`, clamped to
  `[0,1]`, matching WebGL

Effect:

- lens softness parity is no longer capped by the missing
  aberration-derived edge-soften term

#### 3.2.2 Diffusion is now ported to the WebGPU path

Root cause in part 3:

- the UI exposed `diffusion`
- WebGL had a dedicated 3-mip full-image diffusion chain and composite
  blend
- WebGPU still treated diffusion as deferred / unconnected

What landed:

- `diffusion` is packed into the existing 64-byte composite uniform
  layout using `lens.z`
- a dedicated 3-level full-image diffusion pyramid is rendered from
  `rtColorGraded`
- downsample / upsample use `computeMipWeights(0.7, 3)`
- the legacy composite texture slot previously kept for grain-layout
  compatibility is now reused for the diffusion top mip
- the composite shader applies the same screen-blend style diffusion
  formula as WebGL
- diffusion samples use the same flipped-Y convention as
  bloom/halation, without rewriting the existing glow workaround

Effect:

- the user-facing `diffusion` control now does something real on the
  WebGPU path

## 5. Confirmed current root cause of the cross-filter issue

This section is based on direct code inspection of the current
`da74f188` tree.

### 5.1 WebGPU has the cross-filter WGSL shader modules, but not the runtime integration

Confirmed facts:

- `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts` imports and
  compile-validates the five cross-filter WGSL shaders
  (`cross-filter-peak`, `cross-filter-peak-spacing-max`,
  `cross-filter-peak-spacing`, `cross-filter-streak`,
  `cross-filter-blend`)
- `ShaderModules` includes those modules
- but `Pipelines` does NOT include cross-filter render pipelines
- `PrefilterGroupLayouts` does NOT include cross-filter bind-group
  layouts
- `WebGPUBackend` instance state does NOT currently store cross-filter
  render resources analogous to WebGL's threshold / peak / spacing /
  streak / history chain

In other words:

- the shader code exists
- the runtime render graph does not yet use it

### 5.2 WebGPU renderFrame still ignores every cross-filter param

Confirmed facts:

- `renderFrame()` currently executes:
  - filmlab
  - bloom
  - halation
  - diffusion
  - composite
  - post-chain limited to blit / motion blur present path
- the current WebGPU path does NOT branch on:
  - `crossFilterStrength`
  - `crossFilterSpikes`
  - `crossFilterAngle`
  - `crossFilterLength`
  - `crossFilterThreshold`
  - `crossFilterChromatic`
  - `crossFilterSizeLimit`
  - `crossFilterRandomness`
  - `crossFilterHardMode`
  - `crossFilterMinSpacing`
- direct grep shows no `paramNumber("crossFilter...")` reads in the
  WebGPU backend at all

Consequence:

- even if the UI sends non-zero cross-filter params, the WebGPU backend
  stores them in `frameState.params` and then never consumes them
- therefore cross-filter is effectively a no-op on the current WebGPU
  path

### 5.3 Why this was not treated as a v1.0 blocker earlier

Earlier docs deferred cross-filter runtime integration because:

- the WGSL shader port was already compile-validated
- all factory presets in `packages/film-lab-core/src/presets.ts`
  shipped with `crossFilterStrength: 0`
- so the missing runtime path did not affect the factory preset Golden
  acceptance gates used at that time

That historical reasoning was valid for those ship gates, but it is no
longer the correct priority now that the user is explicitly trying to
use the effect.
