### 3.1 New file

- `packages/film-lab-renderer/src/webgpu/shaders/compare-source.frag.wgsl.ts`
  (67 lines including the file-header comment block).

  **WGSL excerpt** (the actual shader body — verbatim, useful for
  debugging without re-reading the file):

  ```wgsl
  struct CompareSource {
    // (resolutionX, resolutionY, imgResX, imgResY)
    resolution: vec4f,
    // (fitMode, _, _, _)
    fit: vec4f,
  };

  @group(1) @binding(0) var<uniform> uCompare: CompareSource;
  @group(1) @binding(1) var uMedia: texture_2d<f32>;
  @group(1) @binding(2) var uSampler: sampler;

  fn fitUv(uv, resolution, imageResolution, fitMode) -> vec2f { /* same math as composite.frag */ }
  fn insideUv(uv) -> f32 { /* step-based [0,1] mask */ }

  @fragment
  fn fs_main(@location(0) uv: vec2f) -> @location(0) vec4f {
    let resolution = uCompare.resolution.xy;
    let imageResolution = uCompare.resolution.zw;
    let fitMode = uCompare.fit.x;
    let mediaUv = fitUv(uv, resolution, imageResolution, fitMode);
    let inside = insideUv(mediaUv);
    let media = textureSampleLevel(uMedia, uSampler, mediaUv, 0.0).rgb;
    return vec4f(media * inside, 1.0);
  }
  ```

  **Bind group layout (3 entries, side-by-side verified with WGSL
  `@binding(0..2)` to avoid the part-9 §5.3 Stream-C miscount class
  of error)**:
  - `binding(0)` uniform buffer (32 B)
  - `binding(1)` texture_2d<f32> (mediaTex)
  - `binding(2)` filtering sampler

## 11. Diagnostic hypotheses (ordered by likelihood, with the next
chat's recommended verification step for each)

### H1 — `setComparePair` is not being called from the UI on WebGPU
(probability: medium-high)

The control panel (`packages/film-lab-ui/src/FilmLabControlPanelCore.tsx`,
lines 445–488) calls `viewport.setComparePair(true, slotA, slotB)`
when `compareOn = supportsABCompare && state.compareMode` is true.
But this only fires when `state.compareMode` flips — which is driven
by the V key handler / A/B Compare button.

For the **Before/After** mode (Space key), the control panel does
NOT call `setComparePair(true, ...)` — instead, it sets `state.beforeAfterStash`
and adjusts `splitPosition`. The actual rendering of "before vs after"
on WebGL relies on the shader's `uAbCompare = 0.0` mode being implicit
when `setComparePair` is OFF and `splitPosition >= 0`. This is **not
ported to WebGPU**: our compare branch only fires when
`frameState.compareEnabled === true`, which only flips via
`setComparePair(true, …)`.

**Verify**: in the running app, attach a `console.log` to
`WebGPUBackend.setComparePair` and confirm whether it's called when
the user presses Space (Before/After) and when the user presses V
(A/B Compare).

If Space doesn't call setComparePair → that's the bug. The fix is
either (a) make Before/After ALSO drive `compareEnabled` via
`setSplitPosition` somehow, or (b) wire the WebGPU compare branch to
fire on `splitPosition >= 0` instead of (or in addition to)
`compareEnabled`.

**This is probably the root cause if the user toggled Space and
nothing happened.**

### H2 — `mediaTexture` is null or stale when compare branch runs
(probability: medium)

The compare branch uses `mediaTexture.createView()` directly (the
local variable from `getActiveMediaTexture(allowPlaceholderMedia)`
earlier in `renderFrame`). If `mediaTexture` is the placeholder
(1×1 black) or hasn't been uploaded yet, the user sees a black
canvas instead of the source.

**Verify**: in the running app, check what `mediaTexture` is
(width/height) when compare is on. Or test specifically with an
image that has been loaded for several seconds (not immediately
after upload).

If the placeholder is the issue, the fix is to gate compare on
"media has been uploaded" (e.g., check `liveVideoElement` OR a
dedicated `mediaUploaded` flag).

### H3 — UI gate doesn't pass even with cap flags flipped
(probability: low-medium)

`FilmLabCanvas.tsx:1159` reads `viewportCapabilities` from React
state. If the state is captured BEFORE Viewport.create resolves with
the WebGPU-flagged capabilities, the gate stays false.

**Verify**: in devtools, inspect the `previewSupportsCompare`
expression value at the moment the user expects compare to work.

### H4 — pipeline runs but writes the wrong texture / wrong format
(probability: low)

Maybe `mediaTexture` (rgba8unorm-srgb) needs explicit color-space
handling that I missed. Or maybe `textureSampleLevel` returns weird
values when the source is sampled at a uv that fitUv pushed outside
[0, 1] (sampler clamp-to-edge should handle this, but worth verifying).

**Verify**: temporarily simplify the WGSL fragment to
`return vec4f(1.0, 0.0, 0.0, 1.0);` and see if the canvas turns
solid red when compare is on. If yes, the pipeline is firing — the
issue is in the texture sample path. If no, the pipeline isn't
firing.

### H5 — pipeline validation error at backend init silently disables
the WebGPU backend (probability: low)

If `compareSourceGroupLayout` or `compareSourcePipeline` fails to
create at `WebGPUBackend.create()`, the entire backend init throws
and the user falls back to the `canvas.webgpuInitFailed` UI. They'd
likely have noticed this (it's a very visible failure mode), but
worth a glance.

**Verify**: in devtools Console, look for `[GpuContext] device lost`
or `[FilmLabCanvas] Viewport.create failed` messages.

### H6 — render-branch ordering issue with motion blur ring
(probability: low)

The new branch is placed BEFORE the `if (!motionBlurOn)` block. When
`compareEnabled` is true and motion blur is on, the ring buffer
doesn't advance that frame. Toggling compare off mid-playback could
produce a discontinuity in the motion blur trail. Probably not the
"not working" symptom but worth knowing.

### H7 — H4 from part-9 (pipeline static validation) re-emerged
(probability: very low — I counted bindings explicitly to avoid the
part-9 §5.3 miscount class)

Already counter-checked side-by-side in §3.1. Mentioned only for
completeness.
