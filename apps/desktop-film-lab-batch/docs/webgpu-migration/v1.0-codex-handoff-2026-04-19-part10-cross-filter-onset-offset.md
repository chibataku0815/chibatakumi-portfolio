## 6. Diagnosis that was reached in this chat

The recommended first attempt in this chat was based on the following
diagnosis.

### 6.1 High-confidence causes

1. **No active temporal hysteresis remains in Hard Mode**
   because the committed baseline intentionally bypasses the temporal
   hold. Current peaks feed central bloom and streak generation
   directly.

2. **The current active path is built from several nonlinear gates**, so
   once temporal smoothing is gone, small luminance changes can look
   like sudden onset/offset:
   - Hard Mode forces a fixed threshold:
     `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts:2237`
   - threshold extraction uses the generic bloom prefilter knee:
     `packages/film-lab-renderer/src/webgpu/shaders/bloom-prefilter.frag.wgsl.ts:30`
   - peak detection uses a local-contrast smoothstep:
     `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-peak.frag.wgsl.ts:64`
   - streak casting originally used hard first-hit logic:
     `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-streak.frag.wgsl.ts`
     before the current unstaged experiment

3. **Spacing is winner-take-all, not attenuative**
   and can therefore blink when highlights compete:
   - `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-peak-spacing.frag.wgsl.ts:40`

4. **Hard Mode still snaps internal policy values**
   rather than interpolating them:
   - threshold forced to `0.7`
   - sizeLimit forced to `1.0`
   - randomness forced to `1.0`

### 6.2 Important interpretation

The most important conclusion was:

- after removing the temporal trail, the visual problem is no longer a
  time-decay bug,
- it is now mostly a **current-frame gate-shape problem**.

That reasoning led to a narrow WebGPU-only experiment instead of
reintroducing temporal hold.

### 7.2 Initial attempt and review feedback

The first version of the experiment was too aggressive.

It triggered two review findings:

1. The first streak-ramp attempt used an absolute width that made Hard
   Mode effectively treat almost any positive peak as eligible.
2. The first threshold-knee widening materially lowered the effective
   onset floor and changed which highlights entered the pipeline,
   rather than only smoothing transition shape.

Those issues were corrected before the user tested the updated version.

### 7.3 Final unstaged experiment that exists now

The current **unstaged** experiment is the adjusted version, not the
earlier over-broad version.

Current unstaged changes:

1. `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts`
   - added internal constants:
     - `CROSS_FILTER_THRESHOLD_KNEE_SOFT = 0.1`
     - `CROSS_FILTER_THRESHOLD_KNEE_HARD = 0.14`
   - wired `effectiveThresholdKnee` into the cross-filter threshold
     pass:
     - current line region:
       `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts:2237-2248`

2. `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-streak.frag.wgsl.ts`
   - replaced hard first-hit threshold with a threshold-relative

     - `PEAK_THRESHOLD_RAMP_FRACTION_SOFT = 0.2`
     - `PEAK_THRESHOLD_RAMP_FRACTION_HARD = 0.4`
   - derives:
     - `peakLower = peakThresh * (1 - rampFraction)`
     - `peakUpper = peakThresh * (1 + rampFraction)`
   - multiplies streak contribution by
     `activation = smoothstep(peakLower, peakUpper, peakLuma)`
   - current line region:
     `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-streak.frag.wgsl.ts:35-37`

## 11. Strong recommendations for the next implementation attempt

These are recommendations, not commands. They are the best current
interpretation of what should happen next.

### 11.1 Do not repeat the same strategy

Avoid repeating either of these ideas in the same form:

- broadening the threshold knee as the primary fix,
- softening the streak ray's first-hit test before the winner is chosen.

Why:

- both ideas modify **which** highlight or sample wins, not just the
  smoothness of the final contribution,
- and the user has already told us the result got worse.

### 11.2 Better next candidates to explore

The next chat should probably focus on one of these instead.

#### Option A: Keep winner selection hard, soften only after selection

Possible direction:

- preserve the original first-hit winner semantics in the streak march,
- once a hit is chosen, soften only the resulting contribution or final
  overlay amount,
- avoid changing the ray's candidate-selection order.

Why this is attractive:

- it targets onset/offset smoothness,
- but does not change which sample "wins" the march.

#### Option B: Address the spacing pass first

Possible direction:

- investigate `crossFilterMinSpacing = 1.00` as the dominant source of
  abrupt blinking,
- replace winner-take-all zeroing with a softer attenuation rule, or
  otherwise reduce binary keep/kill behavior in
  `cross-filter-peak-spacing.frag.wgsl.ts`.

Why this is attractive:

- the user's own evaluation settings maximize spacing behavior,
- and the current spacing pass is explicitly binary.

#### Option C: Add a very short, explicitly time-normalized envelope

Possible direction:

- do **not** restore the old visible trail,
- but consider a very short attack/release envelope that is much shorter
  and less echo-prone than the removed temporal hold,
- only if purely spatial fixes fail.

Why this is lower priority:

- it reintroduces temporal behavior,
- so it must be treated carefully and normalized to elapsed time,
- and it risks re-opening the "afterimage" complaint if overdone.
