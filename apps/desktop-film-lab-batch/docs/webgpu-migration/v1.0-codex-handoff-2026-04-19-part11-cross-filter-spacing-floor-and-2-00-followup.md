## 9. Why `2.00` may feel too weak right now

These are hypotheses grounded in current code, not yet user-verified
conclusions.

### 9.1 The current boost is deliberately modest

In both backends:

- `1.00` already maps to the old maximum spacing radius (`48 px`)
- `2.00` only adds `+24 px` more radius
- so the maximum spacing radius becomes `72 px`, not a dramatic
  multiplier

Relevant current lines:

- WebGPU:
  `packages/film-lab-renderer/src/webgpu/WebGPUBackend.ts:2316-2320`
- WebGL:
  `packages/film-lab-renderer/src/webgl/WebGLBackend.ts:1345-1349`

### 9.2 WebGPU's attenuation shoulder narrows only slightly

The WebGPU near-tie loser shoulder currently changes only from:

- `LOSER_WEIGHT_MAX = 0.06`
- to `LOSER_WEIGHT_MAX_STRONG = 0.02`

That may be too subtle to feel like a large user-facing change.

Relevant current lines:

- `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-peak-spacing.frag.wgsl.ts:28-29`
- `packages/film-lab-renderer/src/webgpu/shaders/cross-filter-peak-spacing.frag.wgsl.ts:75-77`

### 9.3 Hard winner selection still dominates

The spacing pass still preserves hard winner selection.

So even with a larger radius and a slightly tighter loser shoulder:

- winner identity does not change smoothly,
- threshold/peak/streak logic is still mostly the same,
- the parameter may therefore feel less expressive than the user
  expects.

### 9.4 The visible change may be bottlenecked downstream

Possible bottlenecks that may be limiting user-visible change:

- Hard Mode fixed threshold and fixed internal policy snaps
- peak detection density suppression
- streak first-hit logic
- central bloom contribution relative to streak spacing differences
- the fact that the public control currently expands spacing radius only
  after the old `1.00` baseline, rather than changing a more obviously
  visible stage

These are hypotheses only. The next chat should confirm them from
current source and user-visible results.
