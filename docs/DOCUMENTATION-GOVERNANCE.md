# ドキュメント運用ルール

> Status: Canonical
> Scope: `docs/` とリポジトリ直下の運用 README の作成・更新・アーカイブ
> Owner: chibatakumi-portfolio
> Review trigger: 新しい文書領域、所有リポジトリ、または運用責務を追加・変更するとき

## 目的

文書を「探せる」「正本を判断できる」「古い記録を安全に残せる」状態に保つ。新しいファイルを増やすこと自体は目的にしない。

このルールは、このリポジトリの `docs/` とリポジトリ直下の運用 README に適用する。Filmtone、life、または他リポジトリが所有する内容は、それぞれの正本に従う。

## 置き場と責務

| 種別 | 置き場 | 正本の決め方 |
| --- | --- | --- |
| リポジトリ全体の入口 | `README.md` | リポジトリ全体に影響する現在の利用・開発契約 |
| 継続的に参照する実装・運用ガイド | `docs/guides/` または対象コードの近接文書 | 実装・運用の責務を持つリポジトリ |
| 領域固有の判断・根拠 | `docs/<domain>/` | その領域の明示された canonical 文書、またはコード |
| 一時的な計画・引き継ぎ | 原則 life リポジトリ | タスク・進捗の正本は life。ここへ置く場合も完了判定の正本にはしない |
| 変更のない履歴 | `docs/<domain>/archive/` | 後継の正本へのリンクを残す |

`docs/renewal-2026/` は既存の履歴領域である。新しい通常運用・計画・handoff は、life または責務を持つリポジトリへ置く。

## 文書の分類

新規の Markdown 文書は、冒頭に次のいずれかを明記する。既存の履歴文書を一律に書き換える必要はない。

| 分類 | 使う場面 | 必須情報 |
| --- | --- | --- |
| `Canonical` | 現在の仕様・手順・方針の唯一の参照先 | 対象範囲、更新責任、後継または関連する正本 |
| `Operational` | 実行可能な手順・runbook | 前提条件、実行者、完了条件、更新トリガー |
| `Reference` | 調査・設計根拠・比較メモ | 参照時点、適用範囲、現在の仕様との関係 |
| `Historical` | 完了済みの計画・handoff・判断記録 | 完了状態、後継の正本、現行の意思決定権を持たないこと |

例:

```md
> Status: Canonical
> Scope: Portfolio public-site release procedure
> Owner: chibatakumi-portfolio
> Review trigger: Release route, artifact source, or deployment contract changes
```

## 命名と構成

- 安定して参照される正本は、内容を表す短い名前にする。例: `release-procedure.md`。
- 時点に意味がある記録は `YYYY-MM-DD-<scope>-<kind>.md` にする。`kind` は `decision`、`handoff`、`runbook`、`analysis`、`brief` など責務を表す語を使う。
- 新規名に `phase`、`stage`、`step`、`wave` など実装順序だけを表す語を使わない。必要な進行情報は本文に記録する。
- `latest`、`final`、`new` はファイル名に使わない。現在の正本は `README.md` または文書冒頭で指す。
- 画像・比較素材は、その領域の `assets/` または既存の証跡置き場へ置き、本文から用途を示す。

## 正本とリンク

- 同じ契約を複数文書にコピーしない。要約には必ず正本へのリンクを添える。
- コード、設定、公開メタデータが正本の場合は、文書にその優先順位を明記する。
- handoff は作業文脈を渡すための記録であり、仕様・リリース状態・完了判定の正本にはしない。
- リポジトリ外の文書へ案内する場合は、所有リポジトリと理由を記す。ローカル絶対パスは本文の正本リンクに使わない。
- ファイル移動・削除の前に、リポジトリ内リンクとコードコメントからの参照を確認する。後継がない文書は削除せず `archive/` へ移す。

## 更新とアーカイブ

1. 変更対象の情報に既存の正本があるか確認する。
2. 正本を更新し、必要な要約・導線だけを更新する。
3. 古い文書を置き換える場合は、先頭に後継文書と状態を追記してから `archive/` へ移す。
4. 終了した計画・handoff は、新しい作業の入口にせず履歴として扱う。
5. 四半期ごと、または大きなリリース後に `docs/README.md` の入口と正本リンクを見直す。

## 変更時の最小チェック

- リンク先と責務境界が実在するかを確認する。
- 新規文書の分類・対象・正本が分かるかを確認する。
- シークレット、個人情報、ローカル環境固有の値を本文へ書かない。
- 実装契約が変わった場合のみ、該当する Canonical / Operational 文書を同じ変更で更新する。

文書だけの変更に、アプリケーションのテスト実行は要求しない。
