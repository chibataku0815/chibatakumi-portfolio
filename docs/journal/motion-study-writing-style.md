## 2. eyebrow・タイトル・summary

- **eyebrow = 引き出し名そのもの**（ja: 原典一枚絵の表記「増減 / ランダム / 連動 / 反比例 …」・en: 平易英訳「Count growth / Random / Linkage / Inverse proportion …」）。1 語・装飾なし。slug もタイトルも機構側を向くため、「どの技法の記事か」は eyebrow が一目で答える（2026-06-10 ユーザー指摘: 研究語彙の英語 eyebrow「Conservation / Complement」では記事 ↔ 技法の対応が読めない）。対応表の正本は rollout doc の展開表 + 機械ゲートの `DRAWER_EYEBROW`（ja/en とも完全一致を ERROR で強制）
- **タイトル =「<技法名>の作り方」に統一**（eyebrow の引き出し名 +「の作り方」。例:「視差の作り方」「配置移行の作り方」・en は `How to build <X>`）。**2026-06-13 確定**: 旧「〜に見える○○の解剖」型（比喩 +「解剖」）を全廃。比喩は無理に作ると不自然になり（群舞／ダンス等）、「解剖」も日常語でない（ユーザー指摘「無理に表現する必要ない」「解剖も微妙」）。記事の中身は作り方のウォークスルーなので「<技法名>の作り方」が中身そのもの・eyebrow を活かす・全記事を機械的に揃えられる
  - 禁止: 比喩で「〜に見える」と飾る／「解剖」等の硬い語をタイトルに置く／解法の内部語彙を約束の位置に置く／謎かけで引っ張る長文
- **summary = 平易な種明かし**。現象 → 意外な事実 → 仕組みの一言 → 実装形態の順。種明かしの意外性は summary とデモが担い、タイトルは「何の作り方か」を素直に言うだけ

2026-06-11 第 3 次指摘（#4 本文を引用して「ジュニアエンジニアがコードで再現できるとは到底思えない」）への構造対応。過去 2 回の改稿は語彙置換で、骨格には手を付けていなかった: (1) 背骨が「どう突き止めたか」の調査記録で、作り方を探す読者に回り道 (2) 再現の必要条件 — イージングの実数値・座標・コード — が本文に無い (3)「ブラウザのソース表示が仕様書を兼ねる」はミニファイ済み JS への丸投げ。**記事単体で再現が完結する**構成へ改定（ユーザー裁定 = A 案）。

同日ユーザー追補（第 2 ラウンド）: **「定数まで掲載しなくても良い。どう実装するかという考え方の土台こそがメインになるべき」**。仕様書の完全性ではなく**組み立ての考え方**を背骨にする — コード block は全定数表ではなく、読者が自分の数値を入れて動かせる骨格。あわせて**効果・エフェクト（粒状・色収差）は自作パッケージの宣伝枠**と位置づける（チュートリアルにしない）。

**観察・種明かし・なぜ成立・どうやって突き止めたか の独立した「見出し + 段落」は置かない**（2026-06-13 第 8 次）。動きの言葉での描写（観察）はデモが、仕組みの一言（種明かし）と核心（なぜ成立）は組み立て本文が担う。デモと組み立てが重複して説明する節を作らない。仮説の反証・計測の物語（どうやって突き止めたか）は §5 のとおり研究リポの validation record に属する。

**コード block の規律（考え方の土台）**:

- 目的は完全な仕様書ではなく**組み立ての考え方**。フレーム番号 → 各要素の状態を返す純関数の骨格と、「ドライバ 1 本 → 残りは読み替え」の構造を見せ、読者が骨格に自分の数値を入れて動かせる状態をゴールにする
- **値レス骨格型（2026-06-12 第 7 次・ユーザー直指示 — 旧「載せる数値は実値一致」を置換）**: コード block に具体的な数字を載せない。つまみは役割を語る小文字の裸名（`riseStart` / `holdStart` / `slideMax` / `halfTurn`…）で、**宣言せず**自由名のまま使い、冒頭コメントで「小文字の裸名は自分の画面に合わせて決める数」と一度だけ教える。許される数値リテラルは構造の 0 / 1 / 2（値の端点・半分・添字）と普遍的な度数計算の 90 / 180 / 360 のみ。小数はコメント込みで全面禁止。実測値は vendored `verbs/<slug>.params.ts`（ライブデモの駆動側）と研究リポにだけ残る — **骨格に実測値を束縛すると旧コードと完全一致**することを全数サンプリング（Object.is）で証明してから差し替える
- 動きの顔を決めるイージングは `const ease = cubicBezier(...easeHandles);` の形 — 「CSS の `cubic-bezier()` と同じ規格の 4 つの数」への橋渡しを必ず添える（CSS アニメ / Web Animations API / npm `bezier-easing` のどれかで読者がすぐ使える形に）。実値は載せない — カーブの顔は散文が言葉で描写する（「出だしを深く溜めて、終わり際を長くなだらかに」）
- ループの回し方（`requestAnimationFrame` → フレーム番号）と画面への置き方（角度 → 座標など）は、コードか橋渡し段落で必ず 1 度触れる — 「本文の外の知識が要る箇所」を残さない
- コード本体と数値は ja/en で同一。コメントだけ各言語（ja = 日本語 / en = 英語）
- **「ブラウザのソース表示が仕様書を兼ねる」誘導は廃止** — 骨格コード + ライブデモが記事の仕様。ソース表示への言及は任意の補助に格下げ
- **骨格コードは自己完結**（2026-06-11 第 4 次） — code が呼ぶ関数は同記事の code 内に定義する（例外は `cubicBezier` のみ。npm `bezier-easing` への橋渡しを散文に置く）。「キーの間をカーブで埋める」は概念で終わらせず、標準形 `keyAt`（打ったキーフレームのあいだをカーブで埋めて補間する。キーフレーム 1 個 = 「どのフレームで・どの値・次の区間のカーブ」、範囲外は端の値。数字は 0/1 のみの約 11 行）を該当記事ごとに掲載する。キーフレームが 2 個で clamp 1 行で済む記事（master-rotation-echo）は keyAt 不要
- **「キーの表」「表」という名詞は禁止（2026-06-12 ユーザー直指示・2 段階却下）** — `uKeys` 等の配列をデータ構造の造語で呼ばない（「キーの表」「キーフレームの表」とも却下）。AE の語彙だけで書く: キーフレームを**打つ**・あいだは**補間**（カーブで埋める）。配列に触れるときは変数名チップ（`uKeys`）をそのまま指す。en も "key table" / "rows" 禁止 — "the keyframes placed on u" / "fill between placed keyframes" の形。裸の「キー」は打つ系の口語（キーを打つ・止めのキー）としてのみ可で、記事内初出は「キーフレーム」でアンカーする
- **機構は数字を持たない** — keyAt や法則の式そのものに実測値を埋め込まない。第 7 次以降はキーフレームにもつまみの位置にも値を置かない（フレーム位置は `riseStart` のような名前で置く）。分業: 構造と式 = コード / 実値 = vendored params とライブデモ / カーブや大きさの表情 = 散文の言葉
- **機構表現は vendored schedule と等価に** — 見た目がそれらしくても機構が違う骨格は書かない（lattice 事故: 内輪固定 38.1 をリング係数 × 呼吸と誤表現・退場キー欠落）。置き方/回し方の橋渡しは全記事必須（#3 は第 3 次版で回し方が欠けていた）
- **モダン記法で書く（2026-06-11 第 6 次・ユーザー直指示）** — 記事コードは読者にそのまま書いてほしい形の見本。配列の生成・走査は `map` / `flatMap` / `findIndex` / `Array.from` で書き、手書き for / while + push の蓄積は使わない。if の入れ子はアンチパターン — ガード節（早期 return）か三項で平らにする（else-if チェーンは可）。`var` 禁止・`const` 基本。簡潔さは可読性の手段であって目的ではない — ジュニア読者が追えなくなる圧縮（多段ワンライナー等）はしない。**既存コードを書き換えるときは、旧新の出力の完全一致を全数サンプリングで証明してから差し替える**（コメントだけが変わる位置でも証明を省かない）

**末尾 callout（帰属 + 宣伝枠）の規律**:

- プッティさん（@PuttiMW）への帰属は必須・敬称付き
- 仕上げ（粒状・色収差）は**自作の映像仕上げパッケージのショーケース**として 1〜2 文で語る — 「自分たちで開発している仕上げパッケージでライブ合成」+ 自作範囲の明示（イージングのソルバーから粒の乱数まで）。チュートリアルにしない・能力を盛らない（SNS 運用の「スタック表記は自作要素を明示」と同じ路線）。公開導線（解説記事・パッケージページ）が整い次第リンクを足す

各事実は**一度だけ・正しい高度で**語る（タイトル=名指し / summary=種明かし / 本文=論理と数値 / コード block=組み立ての骨格）。同じ事実の三重記述は削る。

## 5. 断定語と数値の規律

- **断定語（のみ / だけ / すべて / 1 個もない / 〜を持たない）は実装と突合してから書く**。量化子は反証可能なロジック主張になる — lattice-breath 改稿で断定語 5 件が構造的虚偽に転んだ前例
- **記事面に具体的な数字を書かない（第 5 次で散文・第 7 次でコードまで拡張 — ユーザー直指示）**。散文の単位付き数値・小数は禁止（第 5 次・CONST_IN_PROSE）、コード block の数値リテラルも構造の 0/1/2 と度数計算の 90/180/360 以外は禁止（第 7 次）。散文はつまみの**名前**（`riseStart`・`slideMax` 等の小文字裸名）で文章を作り、名指す名前は同記事の code に実在させる（UPPER_SNAKE・小文字とも機械チェック）。画面で数えられる個数（「6 個のドット」「キーは 3 個」）は定数でなく構造なので書いてよい。0 と 1 は「0〜1 の値」の端点定義のときだけ可。実測値の正本は vendored params とライブデモ — 記事は形を教え、値は読者が自分で決める
- **検証精度の数値は中心の反証 1 箇所に集約**。小数 3 位の px・誤差倍率はその 1 箇所だけで使い、「なぜその値になるはずか」を 1 文添える（#4: 積一定なら和は落ち込むはず → 76.6px）。他の箇所は「約 5 倍」のような比か定性で言い、比は何と何の比かを同じ文で言い切る
- **計測の内幕（初期値の使い回し・収束・モデル選択スコア）は「癖」の説明 1 文まで**。手順の物語にしない — 読者の本筋は作りであって計測装置ではない（#4 初版はソルバー病理に 2 段落使い指摘を受けた）
- **観察・種明かし・なぜ成立・検証ナラティブ の独立節は載せない（2026-06-12 #8 → #10 / 全記事遡及・§3 と同じ規律）**。「最初の仮説は〜で死んだ / 決め手は〜」型の反証記録は研究リポの validation record に属する。動きの言葉での描写（観察）はデモが見せるので書かない。仕組みの一言（種明かし）と機構の核心（なぜ成立）は組み立て本文に溶かす — 分解の根拠を残すなら機構を主張する節の中の 1 文（「グループ回転を引き算すると残る滑りは直線だった」程度）まで・独立の見出し + 段落にしない
- 数値・採用判断は ja/en で完全一致（ja-writing-style §1 のとおり）
- 帰属は敬称付き: 「プッティさん（@PuttiMW）」。SNS 納品クリップが存在しないセルで bit-parity を主張しない（rollout doc 参照）

## 6. 公開前ゲート（順番に全部）

1. **機械チェック**: `node scripts/check-motion-study-style.mjs <slug>`（または `bun run verify:journal-style` = `--all`）。ERROR ゼロが必須。走査対象は本文 + title / summary / **metaDescription** / **eyebrow**（2026-06-10 拡張 — #4 初版は meta 未走査で「保存量・積保存・棄却」がすり抜けた）。eyebrow は `DRAWER_EYEBROW` の引き出し名と ja/en 完全一致が必須。**2026-06-11 拡張: code block 不在は ERROR**。**2026-06-12 第 7 次拡張: 旧「code 内数値は vendored と一致」を反転 — code block の AST 数値リテラルが白名単 {0,1,2,90,180,360} の外なら ERROR・code 本文の小数はコメント込みで ERROR（値レス骨格の機械化 — §3）。散文の小文字つまみチップ（`riseStart` 等）が同記事 code に実在しなければ ERROR（プラットフォーム名の許可リストあり）**。**同日第 4 次拡張: code が呼ぶ `…At()` 系ヘルパーが同記事の code 内に未定義なら ERROR（自己完結の機械化。`cubicBezier` は許可リスト）**。**同日第 3 次指摘対応: 散文のバッククォートは対（偶数）でないと ERROR（レンダラーが `トークン` を `<code>` チップ化する唯一のインライン記法）・summary / metaDescription にバッククォートがあると ERROR（listing カードと `<meta>` はプレーン表示でパースされない）**。**同日第 5 次拡張: 散文（code 以外の全 block・両 locale）の単位付き数値（°・度・%・フレーム・px・秒・frames・seconds・degrees）と小数は ERROR（CONST_IN_PROSE — マジックナンバー禁止の機械化）・散文が `UPPER_SNAKE` を名指して同記事の code に実在しなければ ERROR（名前ドリフト防止）・title / summary / metaDescription も同 regex で ERROR（コードを併置できない表面は定性表現に開く: 「2 フレームずつ」→「一定の間隔で」）**。**同日第 6 次拡張: code block を acorn AST で走査し、手書きループ（for / for-of / for-in / while / do-while）・if の入れ子（else-if チェーンは除外）・var は ERROR（モダン記法の機械化 — §3）。パース不能な code block も ERROR**。WARN の断定語リストは次工程の監査対象。wave-1 の hold プレースホルダ 4 本（Theatre/boil 系）は legacy 除外 — 公開するならこの型へ移行が先
2. **再構築可能性監査**（手動）: 記事だけを仕様書として「自分が同じものを作れるか」をシミュレートする — (a) 断定語を実装と 1 件ずつ突合 (b) 忠実に従うと別物になる不可視チャンネルがないか (c) **コード block の手順を頭から実行して、本文の外の知識が要る箇所が無いか**（cubic-bezier の橋渡し文・ループの回し方まで）
3. **ユーザー承認**: コミット/push = 本番公開がゲート。本文・タイトル・summary の変更は承認なしに公開しない

## 7. テイストを変えるとき

この型への変更（構成・読者規定・語彙写像の追加削除）は、このファイルを更新してから記事に適用する。記事側で先に逸脱しない。基準記事（lattice-breath）と矛盾する変更を入れた場合は、基準記事も同じコミットで追従させる。
