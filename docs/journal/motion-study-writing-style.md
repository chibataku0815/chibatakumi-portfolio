# Motion-study 執筆スタイル（テイスト固定の正本）

`/journal/motion-studies/` 配下の記事のテイストを固定する。journal 全体の共通規則（常体・backtick・block 別規則）は `ja-writing-style.md` を継承し、このファイルは motion-study 固有の上層を定める。展開順序・ファイルセットは `motion-study-rollout.md`。

**基準記事 = lattice-breath**（2026-06-10 / commit `60e0889a` 時点の本番）。迷ったら本番記事と見比べる: https://www.chibatakumi.studio/journal/motion-studies/lattice-breath

最終更新: 2026-06-10

## 1. 読者規定（ja-writing-style §2 を motion-studies では上書き）

**ジュニアエンジニア・デザイナー**。SNS で見たループの種明かしに来る。

- 既知とみなす語彙: キーフレーム、イージング、`scale`、`SVG`、フレーム、ループ
- 未知とみなす語彙: 参照分解の内部語彙すべて（包絡 / onset / family / 位相 / 写像）
- 判定: 冒頭 2 段落を AE を触ったことがあるだけの人が読んで「これ何?」が連続したら書き直す

経緯: 「同業エンジニア向け・抽象ロジックのみ」型は監査と無駄削減を経て「正確な仕様書」化し却下された。**具体を先に見せてから一般化する**。平易に説明し切ること自体が技術力の証明になる。

## 2. タイトルと summary

- **タイトル = 最短の現象名指し型**（例:「増えて見えるドットの解剖」12 字）。付ける前に「誰がどういう意図で読みに来るか」を 1 文で説明できること
  - 禁止: 解法の内部語彙を約束の位置に置く／誰も持っていない問題の否定形（「〜のキーなし」）／謎かけで引っ張る長文
- **summary = 平易な種明かし**。現象 → 意外な事実 → 仕組みの一言 → 実装形態の順。種明かしの中身は summary が担い、タイトルは現象を名指すだけ

## 3. 本文の雛形（lattice-breath 型・5 セクション）

`sections[]` の構成。block 数は変えてよいが、**この順序と役割**を守る:

| # | block | 役割 | lattice-breath での実例 |
|---|-------|------|------------------------|
| 0 | `motion-demo` | まず見せる（ヘッダ直下） | デモ + 数えられる caption |
| 1 | heading + paragraph | **観察の場面** — デモで読者が確認できる現象を実数値でウォークスルー | 「ドットを数えてみる」6→7→13→19 |
| 2 | paragraph | **種明かし** — 不変量 + 具体のフレーム番号 | 19 個は最初から存在・出現は 10/13/16 フレーム目 |
| 3 | heading + list + paragraph 群 | **作り方** — 配役 list → 駆動源の定義 → 例外チャンネル（あれば仮説棄却の物語と共に） | 「格子と呼吸を用意する」 |
| 4 | heading + paragraph | **表情** — どこに緩急の表情を配り、どこを素のままにしたか = 署名 | 「行きすぎてから戻る」 |
| 5 | heading + paragraph | **持ち帰り** — 純関数の形 + ブラウザのソース表示が仕様書を兼ねる 1 文 | 「再現に必要なのは純関数ひとつ」 |
| 末尾 | `callout` | 帰属 + finish の事実のみ | プッティさん（@PuttiMW）+ `WebGPU` 2 パス |

各事実は**一度だけ・正しい高度で**語る（タイトル=名指し / summary=種明かし / 本文=論理と数値 / ソース表示=全数値）。同じ事実の三重記述は削る。

## 4. 語彙写像（禁止 → 採用）

参照分解の内部語彙は本文に出さない。機械チェック対象。

| 禁止（ja 本文） | 採用 |
|----------------|------|
| 包絡 / エンベロープ / 正規化 | 「〜がどれだけ…かを表す 0〜1 の数値」と初出定義 →「呼吸」等の愛称 |
| onset | 出現（〜フレーム目） |
| family | グループ、または役割名（中心 / 内側の輪 / 外縁） |
| f10・f0–30 記法 | 10 フレーム目・0–30 フレーム |
| キー時刻 | フレーム区間 |
| ハンドル | イージングカーブ |
| schedule 実体 | このページが読み込む JavaScript の定数 |
| view-source（ja 内） | ブラウザのソース表示 |

新しい内部語彙が出そうになったら: (1) 一般語に写像する (2) 写像できない核心語は初出で 1 文定義してから使う。1 概念 1 語（記事内で揺らさない）。

## 5. 断定語と数値の規律

- **断定語（のみ / だけ / すべて / 1 個もない / 〜を持たない）は実装と突合してから書く**。量化子は反証可能なロジック主張になる — lattice-breath 改稿で断定語 5 件が構造的虚偽に転んだ前例
- 本文に出す数値 = 読者が動きを想像できるもの（フレーム番号・%・角度・半径）。全数値の復元経路は「ソース表示が仕様書を兼ねる」の 1 文で誘導
- 数値・採用判断は ja/en で完全一致（ja-writing-style §1 のとおり）
- 帰属は敬称付き: 「プッティさん（@PuttiMW）」。SNS 納品クリップが存在しないセルで bit-parity を主張しない（rollout doc 参照）

## 6. 公開前ゲート（順番に全部）

1. **機械チェック**: `node scripts/check-motion-study-style.mjs <slug>`（または `bun run verify:journal-style` = `--all`）。ERROR ゼロが必須。WARN の断定語リストは次工程の監査対象。wave-1 の hold プレースホルダ 4 本（Theatre/boil 系）は legacy 除外 — 公開するならこの型へ移行が先
2. **再構築可能性監査**（手動）: 記事だけを仕様書として「自分が同じものを作れるか」をシミュレートする — (a) 断定語を実装と 1 件ずつ突合 (b) 忠実に従うと別物になる不可視チャンネルがないか (c) 数値の復元経路が本文にあるか
3. **ユーザー承認**: コミット/push = 本番公開がゲート。本文・タイトル・summary の変更は承認なしに公開しない

## 7. テイストを変えるとき

この型への変更（構成・読者規定・語彙写像の追加削除）は、このファイルを更新してから記事に適用する。記事側で先に逸脱しない。基準記事（lattice-breath）と矛盾する変更を入れた場合は、基準記事も同じコミットで追従させる。
