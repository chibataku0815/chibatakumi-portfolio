## 2. eyebrow・タイトル・summary

- **eyebrow = 引き出し名そのもの**（ja: 原典一枚絵の表記「増減 / ランダム / 連動 / 反比例 …」・en: 平易英訳「Count growth / Random / Linkage / Inverse proportion …」）。1 語・装飾なし。slug もタイトルも機構側を向くため、「どの技法の記事か」は eyebrow が一目で答える（2026-06-10 ユーザー指摘: 研究語彙の英語 eyebrow「Conservation / Complement」では記事 ↔ 技法の対応が読めない）。対応表の正本は rollout doc の展開表 + 機械ゲートの `DRAWER_EYEBROW`（ja/en とも完全一致を ERROR で強制）
- **タイトル = 最短の現象名指し型**（例:「増えて見えるドットの解剖」12 字）。付ける前に「誰がどういう意図で読みに来るか」を 1 文で説明できること
  - 禁止: 解法の内部語彙を約束の位置に置く／誰も持っていない問題の否定形（「〜のキーなし」）／謎かけで引っ張る長文
- **summary = 平易な種明かし**。現象 → 意外な事実 → 仕組みの一言 → 実装形態の順。種明かしの中身は summary が担い、タイトルは現象を名指すだけ

## 3. 本文の雛形（A 案「作り方が背骨」・2026-06-11 改定）

2026-06-11 第 3 次指摘（#4 本文を引用して「ジュニアエンジニアがコードで再現できるとは到底思えない」）への構造対応。過去 2 回の改稿は語彙置換で、骨格には手を付けていなかった: (1) 背骨が「どう突き止めたか」の調査記録で、作り方を探す読者に回り道 (2) 再現の必要条件 — イージングの実数値・座標・コード — が本文に無い (3)「ブラウザのソース表示が仕様書を兼ねる」はミニファイ済み JS への丸投げ。**記事単体で再現が完結する**構成へ改定（ユーザー裁定 = A 案）。

同日ユーザー追補（第 2 ラウンド）: **「定数まで掲載しなくても良い。どう実装するかという考え方の土台こそがメインになるべき」**。仕様書の完全性ではなく**組み立ての考え方**を背骨にする — コード block は全定数表ではなく、読者が自分の数値を入れて動かせる骨格。あわせて**効果・エフェクト（粒状・色収差）は自作パッケージの宣伝枠**と位置づける（チュートリアルにしない）。

2026-06-11 第 4 次追補（再現可能性精査）: 第 3 次版の骨格コードは未定義ヘルパー（`breathAt` / `clipAt` / `angleAt` / `radiusAt`）を呼んでいて、「キーの間をカーブで埋める」が概念のまま一度も式にならなかった — 写経しても動かない。さらに lattice-breath の `dot.ring * radius` は「内側の輪 = 固定半径 38.1」という実機構を「係数 × 呼吸」と誤表現し、scale の退場キーが骨格に無いため 19→6 のカウントダウンが再現不能だった。対策は下の自己完結規律 3 行。

`sections[]` の構成。block 数は変えてよいが、**この順序と役割**を守る:

| # | block | 役割 |
|---|-------|------|
| 0 | `motion-demo` | まず見せる（ヘッダ直下）+ 数えられる caption |
| 1 | heading + paragraph | **観察** — デモで読者が確認できる現象を短く（3〜4 文） |
| 2 | paragraph | **種明かし** — 仕組みの一言 + 意外な事実。調査の物語はここに書かない |
| 3 | heading + list + `code` + paragraph 群 | **組み立ての考え方（記事のメイン）** — 配役 list → **骨格コード block**（ドライバ 1 本 → 残りは読み替え、の構造）→ 橋渡し段落（イージングの当て方・ループの回し方と置き方・差し替えて遊ぶ） |
| 4 | heading + paragraph | **なぜ成立するか** — 機構の核心を 2〜3 文 |
| 5 | heading + paragraph 群 | **どうやって突き止めたか** — 仮説の反証・計測の癖を 1 セクションに圧縮（目安 2〜3 段落・表情/谷と山の話もここへ。旧「最大 2」は公開済み #6 = 3 段落で実態に更新 2026-06-11。#7 初版の 5 段落はユーザー「無駄に長い・再現可能になってない」で却下 → 2 段落へ圧縮 — この目安は実際に守る） |
| 末尾 | `callout` | 帰属 + 仕上げ = **自作パッケージの宣伝枠**（1〜2 文・事実のみ） |

**コード block の規律（考え方の土台）**:

- 目的は完全な仕様書ではなく**組み立ての考え方**。フレーム番号 → 各要素の状態を返す純関数の骨格と、「ドライバ 1 本 → 残りは読み替え」の構造を見せ、読者が骨格に自分の数値を入れて動かせる状態をゴールにする
- **定数の網羅は求めない**（2026-06-11 ユーザー追補 — A 案初版の「全部載せる」を撤回）。ただし**載せる数値は実装の実値と一致**（機械ゲートが vendored `verbs/<slug>.params.ts` / `<slug>.ts` と突合 — 出所不明の数値は ERROR・捏造検知は維持）
- 動きの顔を決めるイージングは「CSS の `cubic-bezier()` と同じ 4 つの数」への橋渡しを必ず添える（CSS アニメ / Web Animations API / npm `bezier-easing` のどれかで読者がすぐ使える形に）。実値は**変えると顔が変わるつまみ**として紹介してよい（必須ではない）
- ループの回し方（`requestAnimationFrame` → フレーム番号）と画面への置き方（角度 → 座標など）は、コードか橋渡し段落で必ず 1 度触れる — 「本文の外の知識が要る箇所」を残さない
- コード本体と数値は ja/en で同一。コメントだけ各言語（ja = 日本語 / en = 英語）
- **「ブラウザのソース表示が仕様書を兼ねる」誘導は廃止** — 骨格コード + ライブデモが記事の仕様。ソース表示への言及は任意の補助に格下げ
- **骨格コードは自己完結**（2026-06-11 第 4 次） — code が呼ぶ関数は同記事の code 内に定義する（例外は `cubicBezier` のみ。npm `bezier-easing` への橋渡しを散文に置く）。「キーの間をカーブで埋める」は概念で終わらせず、標準形 `keyAt`（キーの表 = 1 行が「どのフレームで・どの値・次の区間のカーブ」、範囲外は端の値。数字は 0/1 のみの約 11 行）を該当記事ごとに掲載する。キーが 2 個で clamp 1 行で済む記事（master-rotation-echo）は keyAt 不要
- **機構は数字を持たない** — keyAt や法則の式そのものに実測値を埋め込まない。実測値はキーの表・つまみの位置にだけ現れ、差し替えても構造が壊れないことを散文が言う（定数の網羅撤回と両立する分業: 構造 = コード / 実値 = 表とつまみ / 細部の表情 = 散文）
- **機構表現は vendored schedule と等価に** — 見た目がそれらしくても機構が違う骨格は書かない（lattice 事故: 内輪固定 38.1 をリング係数 × 呼吸と誤表現・退場キー欠落）。置き方/回し方の橋渡しは全記事必須（#3 は第 3 次版で回し方が欠けていた）

**末尾 callout（帰属 + 宣伝枠）の規律**:

- プッティさん（@PuttiMW）への帰属は必須・敬称付き
- 仕上げ（粒状・色収差）は**自作の映像仕上げパッケージのショーケース**として 1〜2 文で語る — 「自分たちで開発している仕上げパッケージでライブ合成」+ 自作範囲の明示（イージングのソルバーから粒の乱数まで）。チュートリアルにしない・能力を盛らない（SNS 運用の「スタック表記は自作要素を明示」と同じ路線）。公開導線（解説記事・パッケージページ）が整い次第リンクを足す

各事実は**一度だけ・正しい高度で**語る（タイトル=名指し / summary=種明かし / 本文=論理と数値 / コード block=組み立ての骨格）。同じ事実の三重記述は削る。

## 5. 断定語と数値の規律

- **断定語（のみ / だけ / すべて / 1 個もない / 〜を持たない）は実装と突合してから書く**。量化子は反証可能なロジック主張になる — lattice-breath 改稿で断定語 5 件が構造的虚偽に転んだ前例
- **散文にマジックナンバーを書かない（2026-06-11 第 5 次・ユーザー直指示）**。コード定数の生値（フレーム番号・px・角度・%・秒・座標・小数）は code block の表の中だけに置き、散文はその**変数名**（`BREATH`・`RAIL`・`RADIUS_REST` 等）で文章を作る。散文が名指す変数は同記事の code に実在させる（名前が無ければ named const を code に足す — その数値は vendored 実装に実在するものに限る）。画面で数えられる個数（「6 個のドット」「キーは 3 個」）は定数でなく構造なので書いてよい。0 と 1 は「0〜1 の値」の端点定義のときだけ可。**数値の網羅は引き続き求めない** — 値の正本は code の表、散文は関係と役割を語る（2026-06-11 第 3 次追補の「本文・コード block に出す数値は実装の実値と一致」は code block 側の規律として存続）
- **検証精度の数値は中心の反証 1 箇所に集約**。小数 3 位の px・誤差倍率はその 1 箇所だけで使い、「なぜその値になるはずか」を 1 文添える（#4: 積一定なら和は落ち込むはず → 76.6px）。他の箇所は「約 5 倍」のような比か定性で言い、比は何と何の比かを同じ文で言い切る
- **計測の内幕（初期値の使い回し・収束・モデル選択スコア）は「癖」の説明 1 文まで**。手順の物語にしない — 読者の本筋は作りであって計測装置ではない（#4 初版はソルバー病理に 2 段落使い指摘を受けた）
- 数値・採用判断は ja/en で完全一致（ja-writing-style §1 のとおり）
- 帰属は敬称付き: 「プッティさん（@PuttiMW）」。SNS 納品クリップが存在しないセルで bit-parity を主張しない（rollout doc 参照）

2. **再構築可能性監査**（手動）: 記事だけを仕様書として「自分が同じものを作れるか」をシミュレートする — (a) 断定語を実装と 1 件ずつ突合 (b) 忠実に従うと別物になる不可視チャンネルがないか (c) **コード block の手順を頭から実行して、本文の外の知識が要る箇所が無いか**（cubic-bezier の橋渡し文・ループの回し方まで）
3. **ユーザー承認**: コミット/push = 本番公開がゲート。本文・タイトル・summary の変更は承認なしに公開しない

## 7. テイストを変えるとき

この型への変更（構成・読者規定・語彙写像の追加削除）は、このファイルを更新してから記事に適用する。記事側で先に逸脱しない。基準記事（lattice-breath）と矛盾する変更を入れた場合は、基準記事も同じコミットで追従させる。
